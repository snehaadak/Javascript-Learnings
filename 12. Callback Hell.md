
- **Problems with callback Functions**

- As we know *Javascript is the synchronous single threaded language it only has single call stack which can execute only one thing at a time. whatever comes first in the call stack is executed first*

- We have something called as *callback Functions* that opens the door to the async world for javascript. We can create a callback function  if we want to execute a particualar part of the code after a pause of some time or some event or some similar situation later.

- But this comes with two major problems faced industry wide those are: 
    1. Callback Hell/ Pyramid of doom
    2. Inversion of Control 


- **Callback Hell/Pyramid of Doom**
    - let's consider a online shopping's after adding to cart procedure as an example. Imagine we have added few itesm to the cart. and the process further is going to be like.....create the order, do the payment, show the order sunmmary, and then update the wallet where each task is dependent on the previous task. Auume that we have api for each task. As each next task is dependent on the previous task it would be the callback function of the previous one.

        const cart = ["Nike Jordans" ,"onitsuka Tigers", "Puma Seudes", "Addidas Sambas"]
            api.createOrder(cart,function(){
                api.proceedPayment(function(){
                    api.showOrderSummary(function(){
                        api.updateWallet()
                    })
                })
            })

    - Now in above case we can see there are number of callback functions dependent on each other. Ther could be possibilty where these callback functions also perform some if else operations or any other conditions or some other functioning. 

    - *When we find one callback inside another callback inside some loops etc, inside another callback this whole chain forms a `callback Hell`. and our code starts to grow horizontally instead of vertically*

    - This type of code structure is unreadable and also unmaintanable. It is tough to manage this type of codes.

    - *This strcuture is also known as `Pyramid of Doom`*


- **Inversion Of Control**
    - It is the another problem that we come across while using callbacks
    - *It is like losing control over our code when using callbacks*
    - Understanding it with the above example.
        In above example we are completely handing over the responsibilty of our whole chain to that one first createOrder api assuming it will run and dependent on that the further callback functions will do.
        This method is verymuch risky as we see one api is callback function to another in above case. Where each api would be written in some different service and we are blindly trusting the createorder api to carry further our whole chain. what id the initial api has bugs in it and the further hain doesnt run, what if due to some reasons our some or the other callback function doesnt run.

    - This above explanation in short means *when we pass a callback function into another function we give our callback function's full control to that outer function or the other piece of code*
