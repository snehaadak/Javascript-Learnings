
- **How JS Engine executes the code**
    - Javascript is a synchronous single threaded language. It just has a single call stack which means it can only do one thing at a time. 
    - This Callstack is present inside the JS engine. and all the code that is executed inside of the call stack in form of small execution contexts.
    - understanding with below example:
        function a () {
            console.log("a");   --> [ a ]
        }
        a();
        console.log("End");     --> [ End ]

    When the above code is executed it executes line by line. As soon as the code starts execution a Global Execution context is created. When first it comes accross the function definition of a and hence allocates the memory space for whole function. on next line when it comes across the the function call for a it creates the execution context for it above the global execution context and puhes the line present in it due to which a is console logged first next when there are no lines present in function a it pops out of the call stack and that EC gets deleted completey. and the code execution moves on next line of global execution context. and hence console.logs End.

    - But what if we have to addin timer based execution how would that work? For these purpose overall JS Engine uses the external superpowers provided to it by the browser.


- **About Browser**

    - Browser has different sections of which one is JS Engine which has the call stack and is responsible for executing our codes. 

    - Along with the `JS engine`, it has the `Local storage` in it where in we can save the local data, we also have a `timer` inside the browser. It also has the superporwer of communicating with the exeternal services and get the data and also help displaying it on the UI.

    - JS engine could make use of these additional Browser's services for timers, for data fetching and etc.


- **Web APIs**
    - Browser helps the JS Engine to make connection with the additional browser services or Web APIs like:
    setTimeout() - *Timer*, DOM APIs - *document.anything we do*, fetch(), local storage, console - *console.log that we do is also the browser's capability that we have.*, location - *anything like http://www. we do*.
    - This connection between the JS Engine and web APIs is possible via the global object i.e window.
    - window is the global object which could be used to access this web APIs by using the keyword window.webAPIname *window.setTimeout(), window.console.log(), window.fetch(), etc.*
    - As we know while using it in the code we dont use the keyword window along with the web APIs it is because it is the global object and has the global scope hence we dont use those keywords


- **Understanding Event Loop and web APIs working:** 
    - considering below piece of code.
        console.log("Start");
        setTimeout(function cb() {
            console.log("Callback");
        }, 5000);
        console.log("End")

    -  When the code starts to execute the very first line in backend makes the web API to the console API which in the end uses the dev tool and prints -- Start
    - When the code execution moves on the next line it comes across the setTimeout API which takes in some callback function and a delay. so when we pass this callback function to setTimeout it registers this callback function in web API's environment. and as we have also passed in the delay it starts the timer along the side. and JS code moves to the next line.
    - The JS code comes across another console API call and does it and on console prints -- End
    - ONCE the whole set of code is completed the Glbal execution context created in very start pops out of callstack. meanwhile this all is happening in backend the timer is still running.
    - As soon as the timer expires after 5000ms(5sec) the callback function needs to be executed. and for it to be executed we somehow need to push that function into the callstack again.
    - Here's when the Event Loop and callback queue comes into the picture.

- **Event Loops & Callback Queue/Task Queue**
    - So in the above example as soon as the timer expires the callback function needs to be pushed into the call stack and that is done through a `callback queue/task queue`.
    - Once the timer expires the callback function moves to the callback queue.
    - We also have the `event loop` acts as a gate keeper who's function is to check the callback queue and pass the functions from call back queue to the callstack.
    - As the timer was over and we have our callback function in the callback queue the event loop pushes this callback function into the call stack and a execution context is created for it. it sees console.log and console API is called and it prints --> Callback
    - *The only major job of event loo is to check whether call stack is empty or not and if the call stack is empty and we have the a function in callback queue it will be pushed inside callstack and would be executed*

    - `Event Loop and callback queue working for DOM APIs`:
        console.log("Start");
        document.getElementById("btn").addEventListener("click", function cb(){
            console.log("Callback on Button Click");
        });
        console.log("End");
    
    The DOM APIs work the same way as setTimeout depending upon what event listner it is attached to as soon as the code execution comes across the eventlistener it attaches the event to the call back function and registers that fucntion on the web API environment. and it will be pushed in the callback queue only on event occurance in our case when that button is clicked.

    - `Event Loop and callback queue working for fetch()`
        console.log("Start");
        fetch("https://api.netflix.com").then(function cb(){
            console.log("Callback Netflix API fetched");
        });
        console.log("End");

        In this case when the code comes across the fetch() it registers the callback function inside the web API environment and alon with that sends the request to netflix server in our case to fetch the required data. and mean time moves ahead with the rest of the code. once the netflix server sends the data back to the fetch and our callback function would be ready to be executed.

- **Micro Task Queue**
    - Now lets consider one more example:
        console.log("Start");
        setTimeout(function cbT(){
            console.log("Timer Ended cbT executed")
        }, 5000);
        fetch("https://api.netflix.com").then(function cbF(){
            console.log("Data Fetched cbF executed")
        });
        console.log("End")

    - Now in above case the first line is executed when the global execution context is created. when the code execution moves to second line it comes across the setTimeout function it register's the cbT in the web API queue and starts the timer. and moves to the next line.
    - In next line it comes across fetch API it registers the cbF and sends request to the netflix server.
    - In next line it comes across the console.log(end) and it is printed so. and the Global execution context deletes completely.
    - let's consider a case where this fetch is completed within the 50ms even before our previous step's timer of 5000ms was over and even tho the cbF is completely ready to be pushed inside the call back queue it wont happen that way. 
    - If the fetch request is completed first it goes inside the microtask queue.all the promises based callback function move to the microtask queue.
    - *Microtask Queue acts as a priority task queue all the network related API calls, promises once ready to be resolved move to this queue.*
    - and further the eventloop tracks the microtask queue, callback queue and the callstack. once the call stack is completely empty the first function to be moved to the call stack would be from the microtask queue. if there are n number of functions in microtask queue they ill be completely emptied first and then once its empty the call back queue functions start to be pushed inside the callstack.
    - output of above code: 
        Start
        End
        Data Fetched cbF executed
        Timer Ended cbT executed

    - *`All the functions based on promises and also the mutation observer(obvserves if there are any changes in the DOM) will go inside the Microtask Queue`*

- **Starvation**
    - If there is a case where there are already alot of functions in micro task queue and if this microtasks creates and pushes more microtasks from themselves among themselves while executing It will hault the callback Queue's execution and this haulting is known as `starvation` of cqllback queue.
